# npjの4分類マスク監査（既知の茶色斑点2箇所）

## 結果

| ページ・手指定範囲 | 黒文字 `02` | 朱文字 `03` | 劣化 `04` | 背景 `05` |
|---|---:|---:|---:|---:|
| hnsd001_011（7,259 px） | 3,474 (47.86%) | 0 | 1,294 (17.83%) | 2,491 (34.32%) |
| hnsd007_042（1,330 px） | 1,330 (100%) | 0 | 0 | 0 |

値の規約は、`02`/`03` は黒 (0) が文字、`04` は白 (255) が実劣化、`05` は白 (255) が背景。各領域内の画素がどの分類マスクに入ったかを数えた。hnsd001では分類が混在し、黒文字・劣化・背景に分かれている。hnsd007ではシミとして手指定した範囲の全画素が黒文字マスクに入っており、劣化マスクには1画素も入っていない。

[2例の4分類マスク比較PNG](hnsd001_011_four_class_audit.png) ／ [hnsd007の比較PNG](hnsd007_042_four_class_audit.png)

## 推論とのつながり

推論コード `pipeline_ddrm.py` は `02_text_black.png` を読み、黒 (0) を復元対象マスクに変換する。`03_text_red.png` はDDRM推論後の朱文字合成に使う。一方で `04_degradation.png` と `05_background.png` はマスク生成時に保存されるものの、DDRM推論経路では読み込まれない。したがって劣化マスクがシミを拾っても、現状のDDRMの復元範囲や条件には反映されない。

今回の2例では、hnsd007の黒文字分類が推論用マスクに入り、シミ領域が文字と同じ扱いになったことは確認できた。hnsd001は一部が黒文字分類、一部が劣化・背景分類で、ひとまとめに「黒文字と誤判定」とは言えない。もし問題の出力で黒く潰れた領域があれば、黒文字マスクに入ったことは有力な原因だが、塗りつぶしの直接原因を確定するには、その出力実行時の保存済み `used_mask` と対応づける必要がある。

## 設計判断

これはDDRM単体の失敗というより、上流の分類誤りと、既にある劣化分類を復元段階で使っていない設計の両方が関係する。今回の証拠は「4クラス分類がシミを正しく分けられている」ことを示していない。hnsd007ではCSC分類自体がシミを文字に取り込んでいる。hnsd001では混在する。

よって、劣化マスクをDDRMへ単純に足すだけで解決とは言えない。先に、(1) シミを含む既存例でCSC各クラスの誤りを測る、(2) 推論時にどのマスクが実際に適用されたかを保存する、(3) 黒文字の保護と汚れ除去を分けて復元へ渡す設計を、固定ページで比較する、の順が妥当。少なくとも現状のまま「npj設計が汚れ除去に十分」と判断する根拠は不足しているが、この2例だけで手法全体が不適切と断定することもできない。

この監査は既知の開発例2箇所に限る。hnsd001は出力を見た後に作った手動範囲、hnsd007も手描き楕円であり、独立評価ではない。文字や汚れの正解ラベルもない。

## hnsd007の推論時マスクとの照合

元の実行フォルダにはパッチごとの `used_mask_raw.png` 自体は残っていなかったため、保存済み入力と保存済みCSCマスクから、コードと同じ変換 `gray(02_text_black) < 127` を再構成した。照合結果は次の通り。

- 全ページのCSC黒文字マスクを推論クロップ位置で切り出すと、推論用に保存されたクロップマスクと全画素一致。
- 推論入力画像も、元ページの同じクロップと全画素一致。
- `pipeline_ddrm.py` が行う変換を適用した再構成マスクは、手指定したシミ範囲1,330画素すべてをDDRMのマスク領域に含む。
- 通常マスクの出力では、その範囲は黒い塊として残る。シミ範囲を黒文字マスクから外して再推論した対照では、手指定範囲の1,330画素すべてが基準出力と異なった。基準出力の同範囲はほぼ黒（RGB平均 0.21, 2.51, 2.03）、マスク変更後は紙色に近い明るさ（RGB平均 211.78, 200.37, 181.54）となり、不自然な白・桃色の穴が生じた。

[推論マスクと出力の拡大比較PNG](hnsd007_used_mask_output_audit.png) ／ [再構成・照合値](hnsd007_used_mask_reconstruction.json)

したがって、黒く残ったシミは推論時のマスクでも文字領域として指定されていた、と結論できる。さらにマスク範囲を変えた再推論で出力も変わったため、この領域の処理結果にマスク指定が関与したことも確認できる。ただしDDRMはパッチ全体の生成出力を返すため、画素単位で黒い塊の全てがマスク値だけに因果的に決まるわけではない。マスクを外すだけでは文字を壊し、穴を作ることも同時に分かった。

注：実行時PNGそのものは保存されていないため、`used_mask_raw` は元の入力・マスク・コード経路が一致することを確認した上での決定的再構成であり、当時のPNGファイルそのものとのバイト比較ではない。
